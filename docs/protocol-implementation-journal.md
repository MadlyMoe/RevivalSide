# RevivalSide protocol implementation journal

The authoritative packet contracts come from the frozen client's decompiled `Assembly-CSharp` tree and `Protocol/ClientPacketId.cs`. `packet-schema.json` records the wire-order census; `protocol/manifest.json` adds client reachability, receive registration, client field consumption, effective RevivalSide ownership, tests, and semantic review status.

## Method

1. Regenerate packet contracts with `npm run generate:packet-schema` after the frozen client changes.
2. Run `npm run protocol:audit` to rebuild the deterministic coverage manifest.
3. Replace every generic hydrated acknowledgement with a domain handler or document an evidence-backed external/unreachable exception in `protocol/coverage-review.json`.
4. Add a focused state-transition or compatibility check and record it as review evidence before assigning `COMPLETE`.
5. Run `npm run check:protocol`; the strict completion gate is `npm run check:protocol:strict`.

## Initial baseline

The checked-in schema contains 1,107 packet contracts: 496 client-to-server, 605 server-to-client, and 6 shared/atypical contracts. RevivalSide recognizes all 496 request opcodes, but 227 effective request registrations currently route through generic hydrated acknowledgements. The initial manifest intentionally labels those `STUB` and labels dedicated but not yet evidence-reviewed paths `PARTIAL`; handler existence alone is not semantic completion.

## Compatibility decisions

- Packet captures are supplemental only. Static frozen-client send references and reflection-registered `OnRecv` methods determine the conservative reachable surface.
- `COMPLETE` is never inferred from a handler filename. It requires an explicit review entry with implementation and test evidence.
- `EXTERNAL_COMPATIBILITY`, `PROVEN_UNREACHABLE`, and `DEAD_LEGACY` require per-packet rationale in the review data.
- Login, lobby initialization, persistence, reconnect, server pushes, and client-consumed response fields remain first-class audit targets.
